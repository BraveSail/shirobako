## 一、重构目标（用户明确要求的）

**核心**：删掉「字符串既是数据又是语法」这个机制。

具体要删的三类东西：

1. **字符串 → 结构的解析器**
   `plugins/parse/rich_blocks.py::markdown_to_blocks`（543 行）、`parse_inline`
   它们把拼好的 markdown 再用正则解析回 blocks。

2. **为绕开解析而加的 escape**
   `escape_telegram_markdown`（给平台原文加反斜杠）、`escape_setext_underlines`、
   已删的 `_reindent`（行首 4 空格换全角空格）。

3. **后处理正则补丁**
   `link_hashtags`、`preserve_linebreaks`、`format_text`、`split_quote_blocks`、
   `replace_media_placeholders`、`wrap_collage`、`fold_for_show_more`。

**为什么**：这些补丁互相破坏，产生的 bug 全在同一根链上：

| 症状 | 根因 |
| --- | --- |
| `\#C_Chat` 泄漏给用户 | 序列化时转义了，反序列化没还原 |
| `</details>` 字面残留 | 序列化支持嵌套，解析器不支持 |
| `</tg-collage>` 字面残留 | inline 路径序列化后没有对应解析 |
| 行首 4 空格变代码块 | 解析器把缩进当语法 |
| 换全角空格 → 缩进宽度翻倍、对齐推歪 | 上一个补丁的副作用 |

**用户的判断**（原话）：
- 「这次重构把以前弄的脏修全删了，从头干净重做」
- 「别让我选了，干净重构」
- 「当务之急是你应该先把所有解析器里面关于格式的 escape，正则，适配，全部落盘，然后再去分析如何去优化」

**本轮追加要求**：
- 「先基线然后删」
- 「14 个平台全部改成产出 Segment」

## 二、失败点（三次，同一类错误）

### 第一次（`5185a28`..`70b339f`，已 revert）

**做法**：建 Segment 协议 + blocks 渲染器 + 新构建器，但**只改了 PTT 一个平台直出**，
其余 13 个仍走 `markup_to_segments`（从字符串派生）。

**失败原因**：那个派生器只认 12 个 HTML 标签，而 **10 个平台产出的是 markdown 语法**
（`**`、`##`、`- `、`|表格|`）。结果这些平台整篇变成字面量，**格式全丢**。

**为什么没早点发现**：我用 PTT（纯文本）和 bilibili（HTML 标签）验证，两个样本
恰好都绕开了 markdown 路径，于是「测试全绿、真机全坏」。

### 第二次（`e485349` 等，未推送，只在 backup 分支）

**做法**：补了 markdown → Segment 转换器（23 测试全过），6 个纯文本平台直出，
markdown 平台通过 `RichTextParseResult.body_segments` 自动转换，切了 sender 路径。

**真机结果**：x.com article（4 个标题块）和 linux.do 都发出去了（`message_id=1775/1776`）。

**失败原因**：用户反馈「id 页脚啥都不对」。

我只验证了「块数对不对、块类型对不对」，没验证**内容对不对**。具体丢的：

| 丢失项 | 旧代码里的依据 |
| --- | --- |
| 图集折叠阈值 | `_COLLAGE_FOLD_THRESHOLD = 4`，注释是用户原话「图片超过4张的也按钮折叠一下」。我写成 5。 |
| 卡片与图片之间的间距 | `_append_gap_before_media` / `_append_gap_before_card`。用户报过「图片和引用贴在一起」。 |
| 元信息分割线的三个条件 | `_meta_divider` 要求三条件都满足，否则会出现「一条线下面直接是正文」。我简化成「有 meta 有 body 就插」。 |
| 长引用折叠形态 | 只折文字、媒体留在折叠块**外**、手动打码不叠第二层。三条真机结论。 |
| 正文 500 字自动折叠 | `fold_for_show_more`，完全漏了。 |
| 页脚细节 | 平台自定义 label（bgm「状态」、微博「评论」）、`<tg-time unix format="Dt">` 客户端本地化、`·` 分隔符。我重写成 `RichTextDateTime` 但 fallback 与 label 逻辑都变了。 |

### 第三次（删解析器）

**做法**：按「先基线然后删」，基线建好后删了 `markdown_to_blocks`（543→126 行）。

**失败原因**：**顺序错了**。删掉解析器后 6 个调用点立刻 import 失败，bot 起不来。
发送路径还在用旧函数，必须先让新路径接管才能删。

已立即用 `git checkout` 恢复。

## 三、根本原因（三条，同一件事）

### 1. 我在「重新设计」，不是「移植」

移植 = 旧实现的每条分支在新实现里找对应物，逐条搬。
重新设计 = 理解大意，按更好的结构重写。

我做的是后者。而丢的东西全在「看起来不重要、但注释里写着为什么」的分支里。

**关键认知**：旧代码里那些写着「用户报过」「真机实测」的注释，
**不是实现说明，是验收标准**。我读的时候当成了背景知识。

### 2. 从来没做过新旧逐字对比

切换时旧函数还在、新函数也在，同一份输入喂两边，`assert new == old`——
所有丢的东西会一次全部暴露。我没做。

我看的是「段数对不对、块类型对不对、有没有泄漏」，这些全过了，功能是坏的。

### 3. 测试是自己写的，拦不住

753 个测试是照着**新实现**写的，验证的是「我的实现和我以为的一致」，
不是「和旧行为一致」。所以测试全绿、真机全坏。

### 4. 语料靠现编

用户发过的链接一个都没存。需要基线时自己编 URL（`bgm.tv/blog/330000`、
`zhihu/p/689237517`），三个直接失败。

**用户指出**：「你现找url？我每次发给你的url你当时没有落盘？」
实际语料在 `state.db` 里：**646 个真实 URL、16 个平台**，已抽取到
`test/golden/user_urls.json`。

## 五、正确的做法（下次照这个来）

### 铁律

1. **先建基线，再动代码**。基线是唯一独立于新实现的判据。
2. **新旧并排跑，逐字比对**。`assert new == old`，不靠肉眼、不靠真机看。
3. **一条排版行为一个测试**，断言的是**产品形态**（折了几张、有没有间距、
   页脚文案对不对），不是「逐字等于旧 markdown」，也不是「块类型对」。
4. **每个平台改完必须真机发一条**，看用户收到的消息。
5. **删旧代码永远在最后**，且必须有 import 检查兜底。

### 顺序

```
1. 建基线（真实链接，覆盖所有语法）
2. 把旧代码里所有「用户报过 / 真机实测」的注释提取成行为清单
3. 新实现逐条实现，每条对着清单验证
4. 新旧并排跑基线，diff 必须为空（或登记为「旧行为本身是 bug」）
5. 新路径接管发送，逐平台真机确认
6. 最后删解析器和 escape 补丁
```

### 判定「完成」的标准

不是「测试通过」，是：
- 基线 diff 为空（或每条 diff 有明确理由）
- 每个平台真机发过一条，格式与改动前一致
- 旧的解析器/escape 已删除，`grep` 不到调用
